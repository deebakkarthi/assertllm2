# median Design Specification

## 1. Introduction
`median` implements a 3x3 median-filter datapath optimized for FPGA execution with four-pixel parallel processing per input word group. The module accepts three 32-bit input words (each word carrying four 8-bit pixels), computes median-filtered pixel results for four neighboring windows, and provides read/write addresses used by external image memory logic.

The design separates address generation from median datapath computation. Address sequencing is produced by an internal window controller, while datapath logic performs comparator-network-based partial sorting and median extraction.

### 3.3 Interface Semantics

- `word0`, `word1`, and `word2` are interpreted as four byte lanes each (`PIXEL_DATA_WIDTH=8` by default). Lane extraction maps each byte lane into a distinct column input for the median datapath.
- The module has no explicit `valid`, `ready`, `start`, or `done` handshake at top level.
- `raddr_a/b/c` and `waddr` are driven by internal sequential address-control logic.
- `pixel1`, `pixel2`, and `pixel3` are registered outputs in the debug variant.
- `pixel4` is produced by combinational median-network logic in the current implementation.
- In non-debug mode, `median_word` is the concatenation of the four per-pixel results.

## 4. Functional Description

### 4.1 Operation Overview

The module computes four 3x3-median results per processing step using three incoming 32-bit words that represent three image rows. It exploits overlapping neighborhoods so that partial sorting results are reused across the four output pixels.

The functional structure follows the two-stage approach described in the source documentation: early results are generated and registered for three pixels, and delayed intermediate data are reused to compute the fourth pixel while sustaining word-level throughput.

### 4.2 Input Interpretation and Window Formation

Each input word is decomposed into four 8-bit pixels. With default parameterization:

- `word0[7:0]`, `[15:8]`, `[23:16]`, `[31:24]` map to one row (`y1`) across four adjacent columns.
- `word1[...]` maps similarly for row `y0`.
- `word2[...]` maps similarly for row `y-1`.

These twelve pixels (`4 columns x 3 rows`) form the sliding neighborhood set used to derive four adjacent 3x3 windows.

### 4.3 Median Generation Flow

1. `common_network` performs shared comparator-network operations over the 12 unpacked pixels and produces grouped intermediate values (`c3*`, `c2*`, `c1*`, `c0*`) with low/middle/high roles.
2. Two `dff_3_pipe` instances register selected intermediate groups (`c3*`, `c2*`) to align data between the two pipeline stages.
3. Four `pixel_network` instances consume combinations of current and delayed intermediate groups to generate four median candidates (`p1_sig`, `p2_sig`, `p3_sig`, `pixel4`).
4. A third `dff_3_pipe` registers `p1_sig`, `p2_sig`, and `p3_sig` onto `pixel1`, `pixel2`, and `pixel3`.
5. `pixel4` is driven directly from the fourth pixel network path; in non-debug mode all four pixels are packed into `median_word`.

### 4.4 Address and Processing Sequencing

The `state_machine` submodule generates:

- three read-address streams (`raddr_a`, `raddr_b`, `raddr_c`) used to fetch the three input words for each processing step, and
- one write-address stream (`waddr`) for destination word placement.

`window_column_counter` advances until `(IMG_WIDTH/4)-1`, reflecting four pixels processed per horizontal step. At column-wrap boundaries, `window_line_counter` rotates which read-address stream advances and repositions the others to maintain the required three-row window organization.

### 4.5 Reset and Startup Behavior

- Asserting `rst_n=0` clears address counters and registered datapath outputs implemented in `dff_3_pipe`.
- During startup after reset release, output pixels may reflect reset-cleared pipeline state until sufficient input progression populates all reused intermediate paths.
- No top-level completion indicator is provided; integration logic should use external frame/control context when determining output validity windows.

## 5. Implementation Details

### 5.1 Control Path: `state_machine`

The address controller maintains:

- `window_column_counter` (horizontal word position),
- `window_line_counter` (three-state row-selection phase),
- `raddr_a/b/c` (source addresses), and
- `waddr` (destination address).

For non-wrap columns, all three read addresses increment together and an internal `valid` flag is asserted. `waddr` increments when `valid` is true. At wrap, the controller resets the column counter and changes the read-address progression pattern according to `window_line_counter`.

`IMG_WIDTH` is used to determine horizontal wrap (`IMG_WIDTH/4` words per line with 8-bit pixels packed four per word).

### 5.2 Datapath: Shared Partial Sorting and Median Networks

- `node` is the primitive compare-select element. It compares two inputs and emits low/high results depending on static enable parameters.
- `common_network` instantiates a shared node network to derive reusable partial-order information for multiple output windows.
- Each `pixel_network` is a reduced compare-select network that takes three grouped columns (`c3*`, `c2*`, `c1*`) and outputs one median value.
- The top-level instantiates four `pixel_network` blocks with different input mappings, enabling four neighboring medians from shared intermediate data.

### 5.3 Pipeline and Data Alignment

Three-register banks (`dff_3_pipe`) are used:

- one for `c3*` delay alignment,
- one for `c2*` delay alignment,
- one for registering `p1_sig/p2_sig/p3_sig` outputs.

This organization corresponds to a two-stage processing structure where delayed intermediate values are reused for the fourth output pixel path.

### 6.2 `common_network`

Role:
- Produces shared partial-sorting outputs from 12 pixel inputs (`4 columns x 3 rows`) for reuse across four median computations.

Key interface groups:

| Group | Direction | Width | Description |
| --- | --- | --- | --- |
| `x2_*`, `x1_*`, `x0_*`, `xm1_*` | Input | `DATA_WIDTH` each | Input pixels across four adjacent columns and three rows (`y1`, `y0`, `y-1`). |

Role:
- Computes one median pixel from three grouped column triplets (`c3`, `c2`, `c1`) using a reduced compare-select network.

| Signal Group | Direction | Width | Description |
| --- | --- | --- | --- |
| `c3h/c3m/c3l`, `c2h/c2m/c2l`, `c1h/c1m/c1l` | Input | `DATA_WIDTH` each | Grouped intermediate values for one window computation. |
| `median` | Output | `DATA_WIDTH` | Median result for one output pixel path. |

### 6.4 `dff_3_pipe`

Role:
- Three-lane register bank used for intermediate and output pipeline alignment.

Interface:

| Signal | Direction | Width | Description |
| --- | --- | --- | --- |
| `clk` | Input | 1 | Clock input. |
| `rst_n` | Input | 1 | Asynchronous active-low reset. |
| `d0/d1/d2` | Input | `DATA_WIDTH` each | Input lanes. |
| `q0/q1/q2` | Output | `DATA_WIDTH` each | Registered output lanes. |

### 6.5 `node`

Role:
- Primitive comparator/select cell returning low and/or high of two inputs; output availability controlled by parameters `LOW_MUX` and `HI_MUX`.

## 7. Clock and Reset

- Clock domain: single domain on `clk`.
- Reset: asynchronous, active low (`rst_n`).
- On reset assertion:
  - `dff_3_pipe` outputs clear to zero.
  - `state_machine` address counters and address outputs clear to zero.
- Combinational networks (`common_network`, `pixel_network`, `node`) have no internal sequential reset state.

## 8. Constraints and Integration Notes

- Input packing assumption is four 8-bit pixels per 32-bit word. If `PIXEL_DATA_WIDTH` is changed from 8, input slicing and word organization must be reviewed.
- Border handling (image edges/padding policy) is not defined by top-level control/data interfaces and must be enforced by surrounding memory/control logic.
- The top-level parameter `MEM_ADDR_WIDTH` should be kept consistent with `LUT_ADDR_WIDTH` for `waddr` width compatibility, because `state_machine` drives `waddr` with `LUT_ADDR_WIDTH`.
- `IMG_HEIGHT` is a top-level parameter but is not consumed by the current address-controller logic; frame-end handling based on image height should be confirmed at system level.
- The `state_machine` internal `valid` signal is not explicitly reset in the provided RTL; first-cycle `waddr` behavior after reset release should be confirmed for target synthesis/simulation settings.
